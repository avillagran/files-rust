# Large progressive JPEG: 1/8 DC preview — 0.0.4 (2026-10-27)

Partial functional unit verified on Omarchy. Baseline 12/24 MP JPEGs already used a reduced IDCT, but many
valid progressive ones were rejected because their full coefficients exceeded 32 MiB.
The new fallback keeps that limit and uses one DC sample per block: 1/8 per axis.
It does not raise 32 MiB or 150 MB; it does not prove the tree's real use while the freeze
remains in effect. The 50 MB goal and the historical baseline/startup FAILs remain open.

The vendored MIT/Apache decoder is kept; libjpeg/IJG was not adopted as a
dependency of files or the helper. No new package, native product FFI, persistent
cache or temporary preview file. The compressed input is lent to the
Cursor; 8 MiB input, 40 Mi pixels/8192 per axis, 3 MiB RGB, 64 scans/1 MiB
metadata and immediate workers are kept. RLIMIT_AS 96 MiB is not PSS. Timeout/cancellation
are supervised through the existing kill/reap, without blocking the UI. The
expected/effective FD signature, the embedded RootProof and the existing cache/renderer are reused.

DC mode only kicks in when the progressive image would exceed 32 MiB of full coefficients;
baseline and small progressive images keep the earlier path. DC initial and
refinement scans are parsed/validated; AC entropy is skipped until the next marker,
so this is NOT an AC integrity check nor a reconstruction at the original
resolution. Malformed headers/DC, duplicates, a wrong scale and missing DC components
fail; corruption confined to AC data may not prevent this preview.
The 1/8 bitmap and the original size are visible in the footer; zoom does not recover detail
that is not in that bitmap. High quality/full chroma and other variants are still
pending; this unit does not close P02 as a whole.

The new path matches the full decoder at 1/8 byte for byte on a
progressive color JPEG generated by ImageMagick, including the DC refinements. An
initial comparison with djpeg 4:2:0 failed (up to 20/255 at the gradient's edges):
it was not the same sampling. A native C probe with the API of the installed libjpeg-turbo 3.2.0
confirms Y IDCT 1×1 but Cb/Cr 2×2, while jpeg-decoder uses 1×1 for all. The earlier
full decoder has the same deviation; it is not attributed to the DC storage and the
threshold is not relaxed to hide it. With 4:4:4 and equivalent scales, the external
reference passes at ≤3/255. Small original synthetic fixtures and commands are in
`crates/helper/tests/fixtures/README.md`; no third-party photo and no new native
build/test requirement for Cargo. The C script is an optional reference, not a product program.

Provenance: the `.crate` SHA matches SOURCE.json, 17 original sources verified,
the patch with fuzz 0 rebuilds the current src exactly, MIT/Apache/README intact.
`evidence/jpeg-dc/vendor-source-review.json`; the scale reference and the initial FAIL
are preserved. The vendor's upstream doctests look for images that are not included and failed;
10 vendor unit tests --lib pass, no false PASS for that command.
